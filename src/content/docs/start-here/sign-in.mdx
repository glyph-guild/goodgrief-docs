After [installing gg](/start-here/install/), two steps remain: tell gg where the organisation's [control plane](/reference/glossary/#control-plane) is, and sign in. The control plane is the service that keeps the record of every flight and decision.

## Before starting: access

Only a member of an organisation can sign in to it. Someone who already belongs creates an invitation link:

```sh
gg invite
```

:::caution[Anyone with the link can join]
Anyone who opens the link can join the organisation. Send it only to the newcomer, in a way both people can trust.
:::

In the console, `i` creates the same link.

## 1. Point gg at the control plane

Ask an administrator for the control-plane address, then run:

```sh
gg config set control-plane <url>
```

This writes the address into gg's configuration file for this machine.

## 2. Sign in

Run:

```sh
gg login
```

gg prints an address and a code, then waits:

```
  Open:  https://<url>/…
  Code:  ABCD-EFGH
```

<Steps>

1. Open the address in a browser. In most terminals the address is a link.
2. Sign in with the organisation's usual account, if asked.
3. Check that the code on the page matches the code gg printed, and approve.

</Steps>

gg notices the approval and prints `Signed in as <name>.` gg stores the session on this machine.

If the code expires before someone approves it, or someone declines the request, gg says so. Run `gg login` again.

When no one is signed in, the console offers the same sign-in: `y` starts it, `o` opens the address in a browser, `l` copies the address and `c` copies the code.

![The gg console when no one is signed in: a window says there is nothing to show yet and offers a Sign in button, and the last line offers y to sign in or esc to carry on signed out.](/screenshots/console/sign-in.svg)

## 3. Check

To see who this machine is signed in as, run:

```sh
gg whoami
```

```
  Person:        Ada Lovelace (3c1f…)
  Organisation:  Example Org (8a2e…)
  Expires:       2026-10-15 02:31:59Z
```

The first line is the person, the second is the organisation, and the third is when this session ends. An administrator also sees a line saying so. Any notices the control plane has for the organisation follow, each with what to do about it.

Then run:

```sh
gg doctor
```

`gg doctor` checks everything gg needs: that gg can reach the control plane, that the control plane speaks a compatible protocol, that this release is the one the organisation expects, that the session is valid, and more. Each problem it reports comes with a line saying how to fix it. When something seems wrong, `gg doctor` is the first thing to run.

If a command later reports that the session is no longer valid, run `gg login` again.

## Signing out

Run:

```sh
gg logout
```

gg asks the control plane to end the session first, then deletes the local copy. If gg cannot reach the control plane, it keeps the local copy and says so. Deleting the copy would leave a session that still works, and that gg could no longer end from this machine. Run `gg logout` again once gg can reach the control plane.

## Where the settings live

gg keeps this machine's settings in one file:

- macOS and Linux: `~/.config/good-grief/config.json`, or under `$XDG_CONFIG_HOME` when that is set;
- Windows: `%APPDATA%\good-grief\config.json`.

To see every setting and where its value came from, run:

```sh
gg config show
```

An environment variable takes precedence over the file. For example, `GG_CONTROL_PLANE` overrides the `control-plane` setting. `gg config show` names which source answered for each setting.

The file names credentials but never holds them. [Add and send credentials](/guides/credentials/) covers credentials.
